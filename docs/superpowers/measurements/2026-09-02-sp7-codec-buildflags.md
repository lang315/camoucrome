## 1. The decision (already resolved — not re-opened here)

`00-conventions.md` §"Proprietary codecs are enabled…" and SP7 D2 (RESOLVED
2026-08-27):

- **Enable for the build:** `proprietary_codecs = true` and
  `ffmpeg_branding = "Chrome"`. Obligatory, not optional: D1 has the fork claim
  Chrome (UA etc.), and conventions forbid SP4 spoofing codec answers the build
  cannot honour. With D1 = Chrome there are exactly two coherent positions —
  enable the codecs, or have SP4 not spoof codec queries at all and accept a live
  tell. This slice takes the first.
- **`is_chrome_branded = true` is NOT the mechanism** — it needs internal Google
  assets the project lacks. The build stays unbranded and matches Chrome's
  *behaviour* through targeted args; `ffmpeg_branding = "Chrome"` is the first.
- **Widevine stays honest.** `enable_widevine` produces no working CDM without the
  separately-distributed binary; `requestMediaKeySystemAccess` must remain real
  (SP4 was scoped to leave it alone). NOT touched here.
- **Distribution licensing remains OPEN, deliberately** (SP7 D2 part 2). Building
  and running locally is narrow; distributing binaries carries H.264/AAC
  patent-pool obligations that Google's Chrome licence does not extend to
  third-party builds. This is explicitly "not a technical call" and is deferred to
  before SP6 ships anything. **This slice enables the codecs for the build; it
  does not resolve distribution.** Flag prominently to the operator.

## 2. The tell being closed (from sp4-media §2.2)

Stock (default GN, `ffmpeg_branding` unset → Chromium branding) `canPlayType` /
`MSE.isTypeSupported`:

| probe | canPlayType | isTypeSupported |
|---|---|---|
| H.264 (`avc1.42E01E`) | `""` | false |
| AAC (`mp4a.40.2`) | `""` | false |
| HEVC (`hvc1…`) | `""` | false |
| MP3 / VP9 / Opus / AV1 | `"probably"` | true |

H.264/AAC/HEVC absent = the classic "not stock Chrome" tell, probed by mainstream
fingerprint libraries and demonstrable by *loading* the media, not just asking.

## 3. The lever

GN args added to the build:
```gn
proprietary_codecs = true
ffmpeg_branding = "Chrome"
```
`ffmpeg_branding = "Chrome"` selects the Chrome-branded ffmpeg config already in
`third_party/ffmpeg` (per-branding × platform × arch, generated by the ffmpeg
roll — no manual ffmpeg regeneration needed); `proprietary_codecs = true` builds
the H.264/AAC/etc. decode paths. After `gn gen`, ninja rebuilds ffmpeg + media +
dependents — a LARGE rebuild (not the incremental few-step builds the Blink
slices did).

## 4. Verification plan

Coherence requires BOTH the API answer AND actual playback (the whole point — a
Blink lie would pass the first and fail the second):

- **C1 (canPlayType):** `video.canPlayType('video/mp4; codecs="avc1.42E01E"')` →
  `"probably"`; AAC → `"probably"`. (Was `""`.)
- **C2 (MSE):** `MediaSource.isTypeSupported('video/mp4; codecs="avc1.42E01E"')`
  → true; AAC → true.
- **C3 (functional playback — the coherence proof):** serve a tiny real H.264
  `.mp4` over the `127.0.0.1` echo_server, `<video>` load it, and assert an actual
  decode signal — `loadeddata`/`canplay` fires and `videoWidth > 0` (a Blink lie
  would `canPlayType`→"probably" but never decode). Run headful under xvfb if a GL/
  video-decode context is needed (mirror the build-tester's headful discipline).
- **C4 (no regression):** VP9/Opus/AV1/MP3 still `"probably"` (already were).

## 6. Operational constraints (build-config SP, not a Blink patch)

- **Rebuild duration** likely exceeds the 10-min Bash tool cap — drive the build
  in the background (`run_in_background`) or a held-open session, NOT a single
  synchronous `contentshell` call, and NOT a subagent (an SSH-master drop mid-build
  kills a subagent with no recovery; the controller is drop-resilient).
- **`gn gen` first** after editing args (the args change is only picked up by a
  regen); confirm the ninja graph actually rebuilds ffmpeg (NON-ZERO, large step
  count) — a 0-step build means the args did not take.
- **Verify headful** for the functional-playback check (C3) if the decode needs a
  real context — content_shell `--ozone-platform=headless` may lack video decode;
  use xvfb + headful, per the build-tester lesson (issue #75).
