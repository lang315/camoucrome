## 2. What follows

Two rows measure as tells the tree can close, both derivations from keys
that already exist (no new key: an independent override would only create
incoherence — conventions rule 4):

1. **Pointer/hover under headless.** The browser fills the WebPreferences
   fields `available_pointer_types` / `primary_pointer_type` /
   `available_hover_types` / `primary_hover_type` from
   `ui::GetAvailablePointerAndHoverTypes()` (no device under ozone
   headless); `WebViewImpl::UpdateSettings` copies them into `Settings`, and
   `MediaValues::CalculateAvailablePointerTypes` & co. read `Settings`.
   Derivation, at the `MediaValues` calculators (`media_values.cc`, the
   file sp4a already hooks, scope from the frame's window): by the claimed
   OS *family* (`camoucfg::ClaimedOs`, kUnknown = no claim = host value):
   Android → `coarse` only, hover `none`; every desktop family → `fine`
   (+ `coarse` when the configured `navigator.maxTouchPoints` > 0), hover
   `hover`. Media queries are window-only: no worker surface.
2. **Touch feature detection.** `'ontouchstart' in window` follows
   `RuntimeEnabledFeatures::TouchEventFeatureDetectionEnabled`, which
   `WebViewImpl::UpdateSettings` sets from
   `prefs.touch_event_feature_detection_enabled` (the browser's answer for
   the host's touch screens; `--touch-events=enabled` forces it on stock).
   Derivation at that call: enabled iff the configured
   `navigator.maxTouchPoints` > 0 (unset: host value). Rule-2
   tension named in the roadmap: `Object.keys(window)` changes by the
   `ontouch*` handler set — which is exactly what a real touch device's
   stock build has, so the invariant is "matches stock *for the claimed
   device*". The windows-keys baseline capture needs a touch condition
   before this ships.

The other rows are closed as measured: no key for the CSS media trio, the
CSS2 keywords and `system-ui` wait on the font-bundle decision.

## 3. Shipped: `d-pointer-touch.patch` (2026-09-11)

Both derivations, as designed in §2, one patch on two Blink files
(`media_values.cc`, the four `Calculate*` pointer/hover functions consult
`ClaimedPointerHover(frame)` first; `web_view_impl.cc`, the
`SetTouchEventFeatureDetectionEnabled` call takes the configured
`navigator.maxTouchPoints` into account). No new key; `gn check` on
`//third_party/blink/renderer/core:core` and `checkdeps` on both
directories clean (the renderer DEPS already grants the four headers).

`scripts/verify_d_pointer_touch.py` (chrome through the client probe, five
launches):

| row | before (RED, unpatched `out/Default`) | after |
|---|---|---|
| V1 no config: host values, V2 differs | FAIL (V2 == V1) | PASS: pointer none, no ontouchstart, 236 keys |

Rule 2 under the touch claim: V3's `Object.keys(window)` equals what the
same binary reports with Chromium's own touch switch and no config —
the four `ontouch*` handlers and nothing else. `measure_d_gaps.py` on the
patched build: the win-touch row now says fine/hover/fine/hover with
`ontouchstart true` in headless, the unconfigured row still says
none/none (rule 5). Regressions after the relink: launcher L1–L5 5/5,
driver sweep six rows `ALL_PASS`. Box commit `90d3548556 d-pointer-touch`,
export gate empty, sync 39.

**Rendered-width follow-up for the CSS2 keywords** (the measurement §1
inferred): the same string set in `font: caption` renders 466.75 px on the
box and 410.03 px on the Mac, and each equals the host's own `system-ui`
fallback width (box 466.75 = DejaVu Sans; Mac 410.03 = Arial, which is
installed there). So the keyword surface is exactly the font-presence
surface; nothing separate to close.
