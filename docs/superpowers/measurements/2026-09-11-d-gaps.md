# D gaps, measured: CSS media, pointer/hover, touch coherence, system-ui

Roadmap step 6: the four "measure first" rows of section D, one pass on the
release `chrome` (the extracted archive of packaging doc §3) through
`scripts/measure_d_gaps.py` — the client probe (patchright) loading one page
that reports everything, four conditions: headless stock (no config),
headless claiming Windows with a touch screen (`ua:osInfo`/`ua:platform`/
`ua:platformVersion`/`navigator.platform` + `navigator.maxTouchPoints 5`),
and the same two headed under WSLg. Reference from stock Chrome on the Mac
(headless, `channel="chrome"`) for the OS-correlated rows. Nothing was
asserted; the table says which rows are tells.

## 2. What follows

Two rows measure as tells the tree can close, both derivations from keys
that already exist (no new key: an independent override would only create
incoherence — conventions rule 4):

1. **Pointer/hover under headless.** Blink gets `available_pointer_types` /
   `available_hover_types` from the browser's `ScreenInfos`
   (`ui::GetAvailablePointerAndHoverTypes`), which in headless has no
   device. Derivation: when a `ua:platform` is configured (a claim exists),
   report a desktop set — `pointer: fine`, `hover: hover`, `any-pointer:
   fine` (+ `coarse` when `navigator.maxTouchPoints` > 0), `any-hover:
   hover`. Where: the `MediaValues` hook sp4a already patched
   (`media_values.cc`), reading the config with the execution context's
   scope. Worker parity: media queries are window-only, no worker surface.
2. **Touch feature detection.** `'ontouchstart' in window` follows
   `RuntimeEnabledFeatures::TouchEventFeatureDetectionEnabled`, set by the
   browser from the host's touch screens. Derivation: enabled iff the
   configured `navigator.maxTouchPoints` > 0 (unset: host value). Rule-2
   tension named in the roadmap: `Object.keys(window)` changes by the
   `ontouch*` handler set — which is exactly what a real touch device's
   stock build has, so the invariant is "matches stock *for the claimed
   device*". The windows-keys baseline capture needs a touch condition
   before this ships.

Neither is in this pass; both are C++ slices with their own verify (RED:
the row above, GREEN: the derived values, plus a stock-vs-fork keys diff
under the touch claim). The other rows are closed as measured: no key for
the CSS media trio or the CSS2 keywords, and `system-ui` waits on the
font-bundle decision.
